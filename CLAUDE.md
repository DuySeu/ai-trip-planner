# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

An AI trip planner: a visitor fills a form (or chats to discover a destination), the backend researches the trip, writes a day-by-day plan, lets the visitor chat to change it, and exports it to `.xlsx` from `data/trip-template.xlsx`.

The approved design is `docs/superpowers/specs/2026-11-16-ai-trip-planner-design.md` and the build plan is `docs/superpowers/plans/2026-11-16-backend-core.md` (ticked steps are done). Read both before adding a feature: they pin table shapes, the plan JSON document, the Excel cell mapping, LLM call budgets and the API. `REQUIREMENTS.md` is the requirement checklist. As of now only plan Tasks 1 and 2 (project setup, schema, migrations) are built; no core logic exists yet. The frontend lives in `frontend/` (not `web/` as the plans say), built from `docs/superpowers/plans/2026-11-16-web-frontend.md` against a mock backend (MSW, `VITE_API_MOCK=true`); `docs/DESIGN.md` is its design guide.

## Commands

Dependencies are managed with uv (`pyproject.toml` + `uv.lock`) and installed into the shared Lab venv at `../.venv` (Python 3.12). Do not create a local `.venv` in this repo: no `uv venv`, no `uv sync`/`uv run` without `UV_PROJECT_ENVIRONMENT=../.venv` (they create `./.venv`). Add a dependency with `uv add --no-sync <pkg>` (`--dev` for tooling), then sync. Keep `--inexact` so packages of the other Lab repos stay installed.

```bash
UV_PROJECT_ENVIRONMENT=../.venv uv sync --inexact   # install everything into ../.venv
docker compose up -d db                   # Postgres 17, credentials from DB_* in .env
PYTHONPATH=src UV_PROJECT_ENVIRONMENT=../.venv uv run python scripts/migrate.py   # apply sql/migrations
UV_PROJECT_ENVIRONMENT=../.venv uv run pytest                             # all tests
UV_PROJECT_ENVIRONMENT=../.venv uv run pytest tests/unit                  # no database needed
UV_PROJECT_ENVIRONMENT=../.venv uv run pytest tests/integration/test_schema.py::test_only_one_active_job_per_trip   # one test
UV_PROJECT_ENVIRONMENT=../.venv uv run ruff check <paths> && UV_PROJECT_ENVIRONMENT=../.venv uv run ruff format <paths>
UV_PROJECT_ENVIRONMENT=../.venv uv run mypy <paths>
PYTHONPATH=src UV_PROJECT_ENVIRONMENT=../.venv uv run uvicorn api.main:app --reload
./scripts/sync_models.sh                  # refresh free OpenRouter model ids
```

Integration tests read `DB_*` (from the environment or `.env`) and run in a separate database `<DB_NAME>_test` on the same server, created on first run; every session drops and recreates its `public` schema. They never touch `DB_NAME` itself.

Ruff and mypy report many errors in the pre-existing template code (`src/models`, `src/agents`, `src/tools`, ...). Lint the files you change, not all of `src/`, unless asked to clean up.

## Architecture

Imports are absolute from `src/` as top-level packages (`from core.settings import ...`, `from db.queries import ...`); pytest adds `src` and the repo root to the path, and anything run directly needs `PYTHONPATH=src`.

Chosen flow (design "Approaches", option 1): a fixed pipeline in code, not an agent loop. Pure `domain` models and rules in the center; `research`, `planning`, `export` depend on `domain`; `chat`, `discovery`, `jobs` add the database; `api` calls services and never runs SQL. Plan generation runs in a separate worker process that leases rows from the `jobs` table (`FOR UPDATE SKIP LOCKED`), no Redis. Every structured LLM output is parsed, validated and repaired once before use; ids, URLs, weather and currency rates are set by code, never by the model.

`src/core/constants.py`: the blocks between `# OPENROUTER...:BEGIN` and `:END` are regenerated by `scripts/sync_models.sh`; do not edit them by hand. Template pieces the new code reuses are listed in `src/CLAUDE.md`.

## Database

- Schema changes are new numbered files in `sql/migrations/` (never edit an applied one). `scripts/migrate.py` applies them in order inside a transaction under an advisory lock and records them in `schema_migrations`.
- Queries live in `sql/queries/<area>.sql` as blocks headed `-- name: <query_name>`, loaded with `db.queries.load_queries`; repositories (plan Task 3) use them with psycopg 3, no ORM.
- Enum-like columns are `text` + `CHECK`, so adding a value is a one-line migration. Business rules the database can hold (30-day trip limit, local currency only abroad, one active job per trip, research rows owned by exactly one of trip or conversation) are constraints, and `tests/integration/test_schema.py` pins them.
- User names are unique on the generated `name_key = lower(btrim(name))`. This relies on Postgres's builtin `C.UTF-8` locale (set via `POSTGRES_INITDB_ARGS` in `docker-compose.yml`) so Vietnamese capitals fold correctly; app code must NFC-normalize names before insert.
- A trip holds one plan (`trips.plan` JSONB); every edit or re-plan overwrites it and no history is kept. Writes bump `trips.plan_revision` and apply only if it still equals the client's value. A re-plan's new request waits in `jobs.request` and is written to the trip together with the new plan.
